## 4. Application Bedrock Client

**File:** `src/shared/bedrock_client.py`

| Aspect | Implementation |
|--------|----------------|
| Client creation | `boto3.client("bedrock-runtime", region_name=constants.BEDROCK_REGION)` |
| API used | `client.converse(...)` (not `invoke_model`, not `converse_stream`) |
| Model ID source | `constants.BEDROCK_MODEL_ID` → `os.environ.get("BEDROCK_MODEL_ID", ...)` |
| Region source | `constants.BEDROCK_REGION` → `os.environ.get("AWS_REGION", "ap-south-1")` |
| Request shape | Model-independent: `messages` / `system` / `inferenceConfig` |
| Text entry point | `invoke_bedrock(prompt, force_json=True, system_prompt=..., max_tokens=..., temperature=...)` |
| Vision entry point | `invoke_bedrock_vision(image_bytes, prompt, image_format="jpeg", ...)` |

**Model ID is never hardcoded at call sites.** It is resolved at call time via
`_model_id()` reading `constants.BEDROCK_MODEL_ID`, which is environment-driven.
A single string literal exists in exactly two places — the Lambda env var
(`template.yaml`) and the local-development fallback (`constants.py`).

**Error handling:**

- JSON parse failure → one retry with a stricter reminder, then `ValueError`.
  Each failure is logged with the attempt number and the first 200 chars of the
  raw response (`logger.warning`) for CloudWatch diagnosis.
- Empty image / oversized image → `ValueError` *before* calling Bedrock.
- Bedrock service errors (`ClientError`, e.g. throttling/access denied) propagate
  to the Lambda handler, which logs and returns HTTP 500. No secrets are logged.
- Nothing logs credentials, headers, or signed material.

**`BEDROCK_REGION` deliberately is not a separate variable.** Lambda injects
`AWS_REGION` automatically and it always equals the deployment region. Adding a
second hardcoded region variable would create a second source of truth that can
drift from the deployment region. `constants.BEDROCK_REGION` reads `AWS_REGION`,

"use `AWS_REGION` correctly where appropriate" without duplicating configuration.

Both `BEDROCK_MODEL_ID` and `BEDROCK_REGION` can be overridden at deploy time
without code changes — no redeploy of source is needed.

**There are no secrets or API keys for Bedrock.** Bedrock uses Lambda's IAM role.

## 11. Problems Found

### P1 — Claude-specific Bedrock implementation (original state)
- **Problem:** Client used `invoke_model()` with `anthropic_version` / Anthropic content blocks.
- **Impact:** Wrong provider for the required Nova 2 Lite configuration; would not work as specified.
- **File:** `src/shared/bedrock_client.py`
- **Recommended fix:** Rewrite on the Converse API.
- **Fixed:** ✅ Yes — client is now `converse()`-only; `grep -rniE "invoke_model|anthropic|openai" src/` returns nothing, and there is exactly one `.converse(` call site (`bedrock_client.py:93`).
  *(The only `invoke_model` text left anywhere is inside `tests/unit/test_bedrock_client.py`, in an assertion that it is **not** called.)*

### P2 — `days_until_expiry` was always `"unknown"` in the recipe prompt
- **Problem:** `generate_recipes` read `item.get("days_until_expiry")`, but no writer ever
  stores that field on `ITEM#` records, so the prompt told the model every item
  expired in "unknown" days.
- **Impact:** The app's headline feature — "prioritise ingredients expiring soonest" —
  was inert. The model had no expiry data to prioritise with.
- **File:** `src/functions/generate_recipes/app.py`
- **Recommended fix:** Derive it from the stored `predicted_expiry`.
- **Fixed:** ✅ Yes — computed via `expiry_predictor.days_until_expiry(date.fromisoformat(predicted_expiry))`,
  rendered as real days, `N (already expired)`, or `unknown` when absent.

### P3 — Model-supplied ingredient IDs were never validated
- **Problem:** Ingredients returned by the model were accepted verbatim. The prompt
  *asked* it to use only available ingredients, but prompt instructions are not enforcement.
- **Impact:** The model could invent ingredients the household does not have; unknown
  IDs silently contributed 0 nutrition, producing recipes with phantom items.
- **File:** `src/functions/generate_recipes/app.py`
- **Recommended fix:** Filter returned IDs against the household inventory set; skip
  recipes left with no valid ingredients; log every discarded ID.
- **Fixed:** ✅ Yes — filtered against `allowed_ids` built from the inventory; discarded
  IDs are logged; recipes with zero matching ingredients are skipped.

### P4 — No image size guard for vision requests
- **Problem:** S3 uploads have no size limit, and image bytes were passed to Converse
  unchecked.
- **Impact:** An oversized upload fails deep inside Bedrock with an opaque error.
- **File:** `src/shared/bedrock_client.py`
- **Recommended fix:** Validate size (and non-emptiness) before the API call.
- **Fixed:** ✅ Yes — `MAX_IMAGE_BYTES = 3_750_000`; empty/oversized images raise a clear
  `ValueError` before any network call.

### P5 — Duplicate EventBridge schedule for the expiry cron
- **Problem:** `ExpiryCheckCronFunction` declares **both** a SAM `Schedule` event
  (`rate(1 day)`) **and** an explicit `ExpiryCheckScheduleRule` (`cron(30 1 * * ? *)`)
  targeting the same function.
- **Impact:** The expiry cron runs **twice daily**, sending duplicate SNS notifications
  to every household.
- **File:** `template.yaml`
- **Recommended fix:** Keep exactly one — delete the `Events.ScheduledCheck` block (the
  resource-based rule has the correct 7 AM IST cron) and keep `ExpiryCheckSchedulePermission`.
- **Fixed:** ❌ **No** — pre-existing and unrelated to Bedrock. Left untouched and reported
  separately, per the "do not silently fix unrelated problems" instruction.

### P6 — Missing `backend/layer/` directory
- **Problem:** `template.yaml` declares `CommonDepsLayer` with `ContentUri: layer/`, but
  that directory did not exist.
- **Impact:** `sam build` fails immediately — nothing can deploy.
- **File:** `backend/layer/` (absent), `template.yaml`
- **Recommended fix:** Create `layer/requirements.txt` (SAM installs it into the layer).
- **Fixed:** ✅ Yes — `layer/requirements.txt` created with `pydantic` (boto3 comes from the runtime).

### P7 — `AWS_LAMBDA_EXEC_WRAPPER` pointed at a non-existent Powertools binary
- **Problem:** Globals set `AWS_LAMBDA_EXEC_WRAPPER: /opt/python/bin/plex`, but Powertools
  is not in `requirements.txt` or the layer, so that binary does not exist at runtime.
- **Impact:** **Every** Lambda invocation would fail at init with `Runtime.ExitError` —
  total outage, not just Bedrock.
- **File:** `template.yaml`
- **Recommended fix:** Remove the variable (the code never imports Powertools).
- **Fixed:** ✅ Yes — removed.

### P8 — Duplicate S3 bucket resource (original state)
- **Problem:** A second `AWS::S3::Bucket` reused `UploadBucket`'s `BucketName`.
- **Impact:** CloudFormation stack creation fails on the name collision.
- **File:** `template.yaml`
- **Recommended fix:** Delete the duplicate; SAM's S3 `Events` already create the notification.
- **Fixed:** ✅ Yes — single S3 bucket now; also fixed bill/fridge routing so both
  ingest Lambdas no longer fire on every upload (type moved to a filename suffix, since
  S3 event filters only support prefix/suffix).

### P9 — SAM deployment artifact bucket does not exist
- **Problem:** `samconfig.toml` sets `s3_bucket = "useitup-sam-deployments"`, but
  `HeadBucket` returns **404 Not Found**.
- **Impact:** `sam deploy` fails before creating anything.
- **File:** `samconfig.toml`
- **Recommended fix:** Create the bucket, or drop the `s3_bucket` line and let
  `sam deploy --guided` create/manage one.
- **Fixed:** ❌ No — requires creating an AWS resource, which needs your explicit go-ahead.

### P10 — SAM CLI not installed locally
- **Problem:** `sam` is not on `PATH`.
- **Impact:** Cannot run `sam validate` / `sam build` locally (substituted
  `cloudformation validate-template`, which passed).
- **Fixed:** ❌ No — environment issue, not a repo defect.

### P11 — Bedrock errors surface as HTTP 500 with raw detail
- **Problem:** A `ClientError` from Bedrock (throttling, access denied) is caught by the
  generic handler and returned as 500 with `detail: str(exc)`. The backend README claims
  raw exception text is never exposed to clients.
- **Impact:** Minor error-semantics/consistency issue; no secret leakage (boto messages
  contain no credentials).
- **File:** all three Bedrock Lambdas
- **Recommended fix:** Catch `botocore.exceptions.ClientError` and map throttling to 429,
  access errors to 502, and stop echoing `detail` to the client.
- **Fixed:** ❌ No — pre-existing pattern across the whole backend; not Bedrock-specific.

### P12 — Invalid SAM policy-template parameter blocked `sam build` / deploy
- **Problem:** `ExpiryCheckCronFunction` used `SNSPublishMessagePolicy` with `TopicArn: !Ref ExpiryNotificationsTopic`. The SAM policy template's required parameter is **`TopicName`**, so the translator failed with
  `InvalidResourceException(... "Following required parameters of template 'SNSPublishMessagePolicy' don't have values: ['TopicName']")`.
- **Impact:** `sam build` and therefore `sam deploy` failed outright — a **hard deployment blocker**.
  Note: `aws cloudformation validate-template` did **not** catch this, because it does not expand SAM policy templates. `sam validate` / `sam build` do.
- **File:** `template.yaml` (line ~379)
- **Recommended fix:** Use `TopicName: !GetAtt ExpiryNotificationsTopic.TopicName`. `!Ref` on an `AWS::SNS::Topic` returns the **ARN**, which is wrong for a parameter named *TopicName*.
- **Fixed:** ✅ Yes — corrected; `sam validate` now reports *"is a valid SAM Template"* and `sam build --use-container` **succeeds**.

### P13 — Shared Lambda layer is declared but never actually used
- **Problem:** `Globals.Function` declares `Layers: [!Ref CommonDepsLayer]` **and** the repo keeps `backend/requirements.txt`. Because each function's `CodeUri` defaults to the template root (`backend/`), SAM's `PythonPipBuilder` finds `requirements.txt` and installs **boto3 + pydantic into every function**, while `layer/` is left unbuilt (the built template still points `ContentUri` at the raw source folder).
- **Impact:** ~**35 MB of dependencies bundled 9×** (~315 MB of build artifacts) and a layer that ships effectively empty. Deploys work but are fat and slow. Not a functional failure.
- **File:** `template.yaml`, `backend/requirements.txt`, `backend/layer/`
- **Recommended fix:** Choose one mechanism, not both:
  (a) **Drop the layer** — delete `CommonDepsLayer`, the `Layers:` entry, and `layer/`; keep `requirements.txt` per-function. Simplest.
  (b) **Make the layer real** — move `CodeUri` to `src/` so SAM stops finding `requirements.txt`, and put pydantic in the layer. *Requires rewriting every `from src.shared import …` to `from shared import …`*, because the zip root changes. Not a small change.
- **Fixed:** ❌ No — not required for Bedrock or for a successful build/deploy; needs a design decision.

## 15. Remaining Manual AWS Steps

Only items that genuinely need AWS Console/manual action:

1. **Create the SAM deployment artifact bucket** (`useitup-sam-deployments`) or drop
   `s3_bucket` from `samconfig.toml` — P9. Not something SAM creates for you when the
   key is pinned in `samconfig.toml`.
2. **Install the AWS SAM CLI + Docker locally** if you want `sam validate` / `sam build`
   / `sam local` on this machine. (Deployment can also be run from anywhere with SAM.)
3. **Confirm Nova 2 Lite model access** is enabled in the Bedrock console for
   `ap-south-1` — already proven working for your account, so this is a confirmation
   only, not an action.
4. **Decide on the duplicate EventBridge schedule** (P5) — a template edit, not a console
   step, but it changes AWS behaviour so it needs your sign-off.

Everything else — IAM role, IAM policies, S3 bucket + notifications, DynamoDB table,
Lambda layer, API Gateway, SNS topic, EventBridge rule — is created by SAM from
`template.yaml`. No manual console setup is required for those.

**Not required:** no Bedrock API keys, no secrets, no OpenAI or Anthropic accounts, and
no environment variables beyond `BEDROCK_MODEL_ID` (already injected).
